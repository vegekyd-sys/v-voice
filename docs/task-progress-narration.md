# 后台任务等待期间的进度播报

豆包和 Grok 直连电话把长任务交给 V 后台（`delegate_to_v`）以后，V 在等待期间会主动说出后台真实进展，不再只在底部显示“后台处理中”。

## 进展从哪里来

- **后台写的公开进展**：沿用 `voice.product.task.read` 的 `progress`，有就优先播。
- **真实工具阶段**：任务由插件方法 `voice.product.task.start` 启动，Gateway 只把这类 run 的工具事件推给会话订阅者。Voice 的 Gateway 连接每次连上都调用 `sessions.subscribe`，然后只认本任务自己的 run 的 `session.tool` 事件；不认的 run 一律忽略。
- **子任务**：后台常把语音任务用 `sessions_spawn` 交给子会话执行。本任务 run 的 `sessions_spawn` 返回 `status:"accepted"` 时，子 run 和子会话也算作本任务，它的步骤同样播报。
- **时长**：没有收到任何阶段时，只说任务已经运行了多久。

工具名映射到固定短语（`task-progress.mjs`），比如 `web_fetch` → “读网页”。不播报工具参数、返回内容、路径或模型推理；不认识的工具只说“第几步”。

## 说什么

V 2026-10-20 的实测：后台每个工具大约 100 毫秒就返回，主要时间花在模型思考上。所以“阶段”是**最近做的那一步**加上一共做了几步：

- “后台正在查记忆。” / “后台正在读网页，这是第4步。”
- “后台刚做完读网页这一步，一共做了5步，还在继续。”
- “刚才有一步没成功，后台还在继续。”
- 阶段没变时的心跳：“后台还在处理，已经40秒了，刚才在读网页。”（时长向下取整）

## 什么时候说

节奏参数在 `session.mjs` 的 `NARRATION_DEFAULTS`：

- 受理后至少 6 秒才说第一句；接单那句话播完、线路空闲才说。
- 换了一类步骤并稳定 2 秒，且距上一句至少 12 秒，才播新阶段；公开进展只需间隔 6 秒。
- 没有新阶段时，第一次心跳在受理后约 15 秒，之后每 30 秒一次；每个任务最多 12 句。
- 用户说话、刚说完（4 秒内）、V 正在播放、Decision 门待定时都不说。
- **还有原生工具在等结果时绝不注入语音**：#28/#34 证明这时注入 `speech_text_buffer.commit` 会让迟到的结果被吞。
- 多人识别（speakerRouting）下，这句话经 `hostSpeech` 作为主机语音通过输出门，不走未经确认的输入回合。
- 结果到达后，等当前这句播完就交付结果，播报不会挡住结果。
- 阶段和心跳只用于电话；音箱/机器人仍只播后台写的公开进展，沿用它们自己的空闲策略。

## 审计

`transcript-log` 只记录 `backend.stage`、`backend.progress-spoken`（kind: fact/stage/heartbeat）、`backend.stages-observed`、`backend.child-run` 的种类和计数；说出的话本身就是 `source:"task-progress"` 的 assistant 字幕，只在实际音频开始时记录。

## 边界

- GPT Live 原生通话不走这条路径，不在本次范围。
- 父任务在派出子任务后提前结束时，语音任务会报失败（另一条线在修“后台任务结束后不通报”）；这种情况下进度播报也随任务结束而停止。
- 合成语音通话验证的是服务端链路和真实后台，不等于真机、手机麦克风或真人体验验收。

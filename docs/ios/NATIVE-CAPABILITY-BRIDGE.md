后台不能依赖 WK 页面一直运行。Apple 的后台执行机制允许系统挂起普通应用，音频等能力有专门的后台执行路径；因此本方案由服务决定、原生执行，页面只负责前台展示。参见 [Apple 后台执行文档](https://developer.apple.com/documentation/uikit/about-the-background-execution-sequence)。这也是我们不把锁屏通话迁回网页麦克风的原因。

## 本次落地的协议

1. iOS 向已有的、带个人绑定认证的 `/api/session` 声明 `nativeRuntimeVersion: 1`。该字段仅选择数据协议，不提供身份或工具权限。
2. relay 会话返回 `nativeRuntime`：版本、播放模式、暂停/插话参数、时长和通话文案。服务端为每通话复制策略，修改策略只影响后续通话。
3. 已协商的 socket 继续先发 `ready`；随后发 `native.runtime`，携带 `voiceSessionId`、严格递增的 `revision` 和通用 `effects`。原生保留 call generation 校验，其他会话、重复/跳号帧、未知操作和整个非法批次均拒绝。
4. `audio.append/clear/complete`、`playback.hold/release` 操作原生音频；响应 ID、迟到 PCM 淘汰、队列上限、排空确认继续由原生可靠执行。服务发来的提示或文本不能自行变成音频。
5. `conversation.row/speakers/mode` 更新有界数据；`surface.notice/phase`、`task.upsert/remove`、`document.present`、`connection.wait/ready` 更新已有系统/网页表面；`call.endWhenDrained/cancelEnd` 复用已有挂断能力。没有任意脚本、URL 抓取、钥匙串、权限或工具执行操作。
6. 新 relay 路径不再把 `speaker.decision`、`injected-speech`、工具名和模型特有事件直接交给 Swift 判断；它们只进入服务端投影器。H5 snapshot 附能力清单，前台重新加载仍读同一个原生 call owner。
7. 旧 build 23、网页与设备未声明版本，继续原协议。新 binary 连接未支持版本的旧服务时才走历史适配器；已协商后禁止退回旧语义。GPT 的现有 WebRTC 适配器独立保留，本次没有改 Gateway 协议/Agent/工具授权。

策略是受限的数值与文本，而不是下载 Swift 或通用脚本。未知操作需要先演进能力协议；不能为了少发版取消输入与权限校验。

## 一个具体例子

以前为一种工具接话增加音频来源标记后，iOS 会根据 source 字符串处理回复归属，后续又需要 build 20 修补通知音频后的旧回复关系。

现在任意来源的服务端接话先变成同一个 `audio.append`。服务明确是否允许局部声音探测打断，字幕变成稳定 ID 的完整行；iOS 不知道这句话来自搜索、记忆还是将来新增的插语场景。内容与模型规则在服务迭代，音频执行器仍保留旧回复淘汰和队列保护。

执行器自身有缺陷仍应修原生。这个改造减少的是产品策略导致的安装包改动，不能承诺永远不再升级 App。

## 开发与验证约定

- 对话产品改动先做在 Web/服务，使用既有能力操作。除非新增原生执行能力，不添加 Swift 的 provider/source/中文关键词分支。
- 新模型先声明已支持的传输能力。未知传输显示不可用；不得让任意模型 ID 自行选择系统权限或私有 API。
- 现有测试服务端模拟真实 H5 HTTP、relay 与 provider adapter，使用合成 PCM 和本地 mock 上游，无真实模型/工具请求、无录音。
- 同一个 `CallCoordinator`、同一个 App 二进制连续拨两通本地 fixture；只改变服务端接通文案和暂停 onset 从 140ms 到 220ms。相同 160ms 合成输入在前者暂停、后者不暂停；没有 WKWebView 实例，证明后台能力不需要前台 JS。
- 保留通用操作跨语言 wire fixture、外部会话/重放/未知权限操作/非法混合批次拒绝测试，以及旧客户端兼容和旧尾音/旁聊恢复/最终排空挂断的完整链路回归。
- iOS 测试使用本会话已有的独立模拟器、29937/29947 端口，不触碰实体机和共享测试机。模拟器通过仍不等于真实后台收音、Action Button 或灵动岛按键已验收。

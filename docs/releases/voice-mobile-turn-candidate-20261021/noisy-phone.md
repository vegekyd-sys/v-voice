# 嘈杂环境下请求被替换：候选修订

日期：2026-10-21。运行提交 `3ca92841546f3c3042dc8888ad6447e6f4c9af7a`，候选版本 `voice-mobile-turn.20261021.4`。独立 Candidate，未合入或发布正式服。

## 现场时间线

用户报告 10:50:58 开始的物理 iPhone Safari 通话，在嘈杂环境中前一分钟难以聊起来。服务端记录支持两个不同的原因：

| 相对拨号时间 | 实际观察 |
| --- | --- |
| 约 5.2–10.3 秒 | 上传计数停住，麦克风 muted，AudioContext 曾 suspended；页面一直前台。最大采集帧间隔 5070 ms，之后恢复。用户补充开头有系统电话打入，与系统音频占用吻合；没有 OS 日志证明内部触发细节。 |
| 25.65 秒 | 一项完整 NBA 查询获准回应。 |
| 33.79 / 34.63 秒 | 已实际调用搜索并交付结果，不能归因为完全没有执行工具。 |
| 37.08 / 47.08 / 50.14 秒 | 三个疑似背景声或回声的片段获准替换当前请求；分别走 fallback，清除旧生成并重新输入音频。原音频未保存，不能确认每个声源。 |
| 63.69 / 76.80 秒 | 用户再次提出查询获准，后续才有完整语音答复。 |

三个片段没有达到现有 directlyAddressed 判断；quiet 概率分别为 0.48、0.58、0.62，其中后两条原始 action 是 quiet，却被面向普通聊天的“不确定静默兜底”改为 respond。结果是：原查询已经执行，仍被含糊的新输入连续替换，用户听不到完整结果。

系统来电期间 Safari 的音频暂停不能靠服务端重放恢复未采集的语音；该段不能当作本修订的降噪验收。恢复后持续卡顿也不能全部归因于来电。

## 针对性修复

将“普通聊天可接话”与“替换正在回答或查询的请求”分开。流式服务在已有获准话轮需要保护时，把 interrupting 状态交给既有语义判定器。没有明确对 V 说话的证据、action 证据也不足时，不允许借聊天兜底替换原请求；保留原输入、输出门和恢复计时器。明确面向 V 的新请求与已确认告别仍可打断。

被阻止的插话不切换主要对象、不修改人物属性，也不进入 activeConversation。诊断保留有界的 addressed 概率及 interrupting 状态，不新增原声或被拦正文留存。未增加模型请求、关键词规则、Gateway 改动或工具授权。

## 验证与边界

- 主套件 651/651，speaker-native 88/88，Linux Node 22 七个相关文件 180/180。
- 回归使用现场的三组 quiet 概率，覆盖低置信度 respond 与 uncertain-quiet 两条路径：连续三个片段不能取消原查询，原工具和音频可交付，后续明确请求仍能替换。另验证被阻止的插话不改变 focus 或污染获准上下文。
- 真实模型文本回归 10/10：话题评论、任务补充放行，旁聊、独立附和、广播安静。
- 真实候选音频链路：发起查询，在工具开始后插入一个本地合成片段。实际判定 quiet=0.66、addressed V=0.38，reason=uncertain-interruption；片段未放行，原输出未被清除，原搜索和语音完成。之后明确追加第二项查询，实际调用工具并返回语音。五项检查全部通过。
- 上述音频是本地合成语音，经真实 ASR、语义判定和原生模型。没有重放用户原始录音，没有复现真实现场的全部混音、回声、声压或系统来电，仍待同一嘈杂环境物理手机验收。
- 合法话轮若走 fallback，仍存在整句实时重放成本；现场一项约 5.3 秒的输入重放也耗时约 5.4 秒。本修订减少误替换和无效重放，不代表所有对话延迟已解决。

# 接通速度：分段实测与同次拨号并行

状态：2026-11-12 18:25 CST，代码在分支 `claude/voice-connect-speed`，未合入、未发布。没有真实拨号验证，下面的“之后”数字来自本地仿真。

## 生产实测（豆包，当前生产 `9eb75eb`）

数据来自生产通话审计里的 `call.admission-timing` 和 `call.connection-stage`，只取计时字段。2026-11-06 起经飞书身份接入的 14 通：

| 阶段 | 做什么 | 中位数 | 范围 |
| --- | --- | ---: | ---: |
| 准入 | `voice.feishu.resolve`，Gateway 实时校验群成员身份 | 1.1 s | 0.6–1.6 s，一次 7.1 s |
| 环境 | `tools.catalog` 和 `chat.history` 并行读取 | 0.7 s | 0.6–2.4 s |
| 上游 | 连接豆包并建会话 | 0.45 s | 0.4–0.5 s |
| 问候 | 服务端就绪到第一段问候音频 | 0.9 s | 0.8–1.75 s |

三段串行，服务端从收到拨号到就绪约 2.2 s，慢的时候 4 s，最差一次 9 s。再加手机到入口的握手、首次取麦克风和问候，就是体感的 6–8 秒。

两个原因：

- 经飞书身份的每个 Gateway 请求都各自做一次成员校验，约 0.6 s。准入、工具目录、历史三个请求里，准入和后两个是串行的。11-05 之前走个人入口的通话没有这层校验，环境读取只要 0.07–0.13 s。
- 问候要等页面收到“就绪”后再发一次请求，跨境链路上这一来一回占 0.5–1.4 s。

GPT Live 近十天没有网页或手机通话，生产里没有分段数据，本轮没有实测。

## 改动

1. **准入与环境读取并行。** 目录记住某个身份上次被准入到哪个会话，只作为“可以提前读什么”的提示。拨号时准入还在路上，就用这个提示发出工具目录和历史读取。Gateway 对每个提前读取照常做成员校验；准入返回的会话与提示一致才采用，不一致、被拒或取消就丢弃。准入本身没有省略，也没有跨拨号复用。
2. **提前连上豆包。** 同一时间打开上游连接，不建会话、不发指令和音频；准入通过后在这条连接上建会话，未采用就关闭。
3. **问候不再多等一个来回。** 页面拿到拨号连接就请求问候，服务端在就绪那一刻播出。就绪后页面照旧再请求一次，旧服务端行为不变。
4. **麦克风和拨号并行。** 浏览器已授权麦克风时两者同时开始；可能弹授权框时保持原顺序，用户允许前不创建通话。GPT Live 的建会话请求同样受益。

采用后的快照仍受原有一秒交接窗口约束，工具调用前的实时检查不变。阶段审计新增 `admitted` 和 `prefetch-failed`；采用并行时各阶段的 `elapsedMs` 从收到拨号起算，包含准入，与旧数据对比时要注意。

| | 之前 | 之后 |
| --- | ---: | ---: |
| 页面收到就绪 | 3.0 s | 1.66 s |

这只说明各阶段怎样叠加，不是手机实测。

## 没有解决的

- 接通时间现在等于准入那一次成员校验的时间。它中位 1.1 s，偶发 7 s；要稳定进 2 秒并消掉长尾，需要平台侧让同一身份的校验在几秒内合并或缓存，属于 `v-openclaw-platform` 的改动。
- iOS 原生拨号自动得到第 1、2 项；第 3 项需要原生端在收到 reservation 时请求问候，要出新版本。
- 音箱和小机器人走上海节点的设备通道，不经过飞书身份校验，本轮没有改动也没有测。
- GPT Live 的会话创建和 SDP 交换在 Gateway 与 OpenAI 之间，本轮只让麦克风与建会话并行。

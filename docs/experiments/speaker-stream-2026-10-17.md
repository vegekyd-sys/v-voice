# 豆包流式多人候选验证 · 2026-10-17

版本：`speaker-stream-candidate.20261017`。分支：`codex/volc-speaker-modes`，基于先前候选 commit `629d10f`。产品入口26325，旧串行候选26320保留。没有合入、部署或重启生产，也没有修改共享 VLab/Gateway 核心。Voice 内部适配复用已有 Gateway 接口，本轮在独立 Candidate 验收。

## 方案与实际接口结论

目标为豆包保留原生语音，同时减少等待分人后整句重放的延迟。GPT Live 停止额外多人适配，走原生路径。

- 云端流式 ASR 的中间结果在本次探测中没有 `speaker_id`，最终 definite 结果才带编号；不能把“流式 ASR”当作已支持稳定的早期分人。
- 小何 `session.update`/上下文消息得到 ACK 后，本次真实探测仍出现人物表达滞后一轮。把身份中途更新后放行不能保证当轮正确。
- 增加本地 sherpa-onnx/WeSpeaker Chinese，约1秒语音建立当次匿名声线，无预注册或人工校准。合成样本 CPU 推理中位数19.13ms；不代表真人/远场精度。
- 已知人物以正确 persona 启动/复用原生连接，带短缓冲边听边传。ASR最终文本交 Decision 判断关系/接话/对象；音频、字幕、工具与提示语全部等 Decision 后释放。拒绝则一起丢弃。
- 首次获得姓名/角色、人物或回答对象组合变更时，丢弃原待播回答，用正确启动信息重建原生会话并保守送该句。稳定轮次快，切换轮次仍有代价。不是所有模式都省掉整句重放。
- 普通自动模式允许未确认的短音频先到小何，输出/工具门控负责拦截；明确排他后，其他已知声线在输入端拦住。没有实现音源分离或现实身份认证。
- 后台任务保留原 native owner；切换人物后迟到结果只显示在屏幕，不交给新人物的语音会话。账号和权限不随 Speaker 切换。

## 相同单句对照

同一段3.624秒合成问题，相同小何 `1.2.6.1/xiaohe`，相同独立私有 Gateway，顺序运行避免同时负载。计时从实际合成发言结束到**服务端第一包真正原生回答 PCM**；排除缓存“我查一下”。不包括拨号、浏览器120ms预缓冲、扬声器延迟；不是生产拨号测速。

| 路线 | 成功轮次，秒 | 中位数 |
|---|---|---:|
| 旧串行 Speaker+Decision+小何，26320 | 13.334 / 8.141 / 9.512 | 9.512 s |
| 新流式多人，26325 | 3.663 / 8.138 / 3.974 | 3.974 s |
| 原生小何对照，同候选关闭门控 | 4.399 / 3.243 / 3.749 | 3.749 s |

新流式成功样本中位数降低58.2%，较原生对照多0.225秒。但样本很小，最慢仍8.138秒，不能承诺所有轮次同样快。新路线第三次首次尝试因“语音或工具环境尚未就绪”无输入失败；表中3.974秒来自重试，原失败收据保留。是3次成功/4次尝试，不能将其当作3/3稳定通过。

新路线单句均出现 `stream-accepted`，避免约4.01秒 ASR片段重放。原生连接准备约0.96–1.36秒，输入缓冲约1.98–2.40秒。第2次新路线及部分原生/旧路线仍触发额外查网/后台补充，造成长尾与重复答案。新 persona 明确普通科普直接回答，但保留全部原生工具，因此这是方案整体对比，不能将全部差值归因于传输协议。

私有环境没有完整生产记忆/飞书频道/个人工具凭据；原生对照不是生产上下文逐字节镜像。实际 API 总账单未统一取得，不报告推算费用。

## 多人效果

使用同一108.936秒合成父子7句语料，无预先声纹；孩子角色由另一成人合成音色扮演，并非真实儿童音频。最终 `stream-quality-r3` 传输完成，无路由错误，收到真实原生PCM与完整字幕。

| 场景 | 最终观察 |
|---|---|
| 父子自我介绍 | 稳定为A/local0与B/local1；姓名关联天意、12，角色adult/child。首句父亲介绍判断为安静，未单独口头确认 |
| 孩子问月亮 | 回应对象B，角色首次确认后正确persona重连，再生成原生回答 |
| 递杯子旁话 | Decision quiet，待播音频/工具不放行 |
| 分别给父子建议 | 对象A+B；实际回复分别提及双方与建议 |
| 只跟十二聊 | mode=exclusive，target=B |
| 父亲旁话 | withheld，modelCalled=false；没有该句 native 输入启动 |
| 十二继续听故事 | 对象B，stream-accepted，省掉5.1秒重放，实际原生故事字幕/PCM |

未把回答科学准确性、自然听感、真人身份精度或重叠分离宣称为通过。部分科普表述仍过度简化；完整故事 PCM 返回不等于扬声器全程听感验收。

## 暴露并修复的问题

1. 多人第一轮：人物切换时旧后台任务跟随新 bridge，导致通话关闭。改为 task owner、保留有限 retired bridge、旧结果屏幕交付；补两个真实 adapter 层回归。
2. 多人第二轮：ASR 合并的一句包含未确认短声线，答复一直待播后溢出。增加整句声线复核、逐句拒绝/恢复；第三轮完整跑通。
3. 连续同声线第一轮：第三个问题 Decision 超时关闭了通话。改为丢弃该句全部输出/工具、保留电话、下一句可继续；补超时后同通话恢复测试。超时不会旁路过滤。该旧失败收据保留，不合并进成功统计。
4. 连续同声线第二轮：没有传输错误，但首个问题漏答，不能算效果通过。定位到取消的待播回答残留 nativeBusy，下一句误走保守回退，慢连接进一步延迟；清除拒绝轮的忙碌标记，并忽略已关闭门控收到的迟到音频。补“旁话取消后下一句仍可流式启动”的回归。验证器增加逐问题响应窗口，不能只凭整通收到过音频就判通过；原始第二轮收据的 passed 只是旧传输判定。

内置浏览器在真实产品执行合成问题，气泡显示 Speaker A，原生答复正常；AudioWorklet 播放活动从 speaking=true 到false，随后保持 listening；控制台无错误/警告。实际浏览器首段播放活动在发言结束后4.046秒，包含播放缓冲。这是浏览器回放证据，仍不等于真人父子麦克风/扬声器听感验收。已结束测试电话，页面回到无 query 的普通拨号入口。

## 连续会话最终复验

相同93536ms合成序列：自我介绍后，同一声线间隔20秒连续问三个相同问题。旧串行 `serial-steady-r2` 和修复后的新流式 `stream-steady-r3` 三个问题均有原生回答，逐句检查未漏答；不能仅凭脚本旧版 passed 判定。

| 轮次 | 旧串行 | 新流式 |
|---|---:|---:|
| 介绍后第一个问题 | 10.351 s | 9.507 s |
| 第二个问题 | 7.071 s | 2.994 s |
| 第三个问题 | 7.660 s | 3.171 s |

新流式三轮全部 `stream-accepted`；后两轮 prepareMs=0，缓冲1.02/1.04秒，证明复用已有正确人物连接并避免整句重放。第一个问题准备2.001秒且仍查网/后台补充，故仍慢，不能只展示后两轮称为全程3秒。新旧本轮都出现非必要查网和重复补充，这个原生工具策略问题未完全解决。实际旧串行首次稳态尝试因环境未就绪失败，重试才完成；失败收据保留。

交付时26325和26320均 ready=true、activeCall=false；新流式由独立 launchd 进程管理。浏览器已展示26325正常拨号入口，默认豆包；未打开人的麦克风录制，也未把合成回放算作真人验收。
